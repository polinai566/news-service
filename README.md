# Новостной сервис

## Описание сервиса

При помощи новостного сервиса можно: 
- регистрировать, изменять, удалять и получать пользователей (сущность User)
- создавать, изменять, удалять и получать новости (сущность News) и комментарии к новостям (сущность Comment)
- авторизовывать пользователей (то есть, создавать для них сессии), получать и удалять сессии и обновлять их при помощи refresh токенов
- авторизовывать пользователей через GitHub
- отправлять пользователям на почту (логировать и сохранять в файл) моковые уведомления при создании новой новости, а также еженедельный дайджест каждое воскресенье при помощи Celery

Также в данном новостном сервисе реализовано кэширование новостей посредством СУБД Redis класса NoSQL. \
Новости сохраняются в кэш при получении (GET запросе) с TTL, равным 5-ти минутам. \
Сессии целиком храняться в Redis с TTL, равным времени жизни соответствующего refresh токена.

## Шаги для запуска сервиса

1. Создать файл .env со строками по следующему образцу:

    ASYNC_DATABASE_URL=postgresql+asyncpg://postgres:password@localhost:5432/db \
    SYNC_DATABASE_URL=postgresql://postgres:password@localhost:5432/db \
    JWT_SECRET_KEY=your-secret-key \
    JWT_LIFETIME_MINUTES=10 \
    REFRESH_TOKEN_LIFETIME_DAYS=1 \
    GITHUB_CLIENT_ID=your-client-id \
    GITHUB_CLIENT_SECRET=your-client-secret \
    GITHUB_CLIENT_REDIRECT=http://localhost:8000/session/auth/callback \
    REDIS_HOST=localhost \
    REDIS_PORT=6379 \
    LOGSTASH_HOST=localhost \
    LOGSTASH_PORT=5000 \
    HAWK_DSN=your-hawk-dsn
    
    Для получения Client ID, Client Secret и Client Redirect:

    - перейдите по ссылке: https://github.com/settings/developers
    - нажмите **Новое приложение OAuth** и заполните обязательные поля (в частности Client Redirect)
    - нажмите **Зарегистрировать заявку**
    - после регистрации GitHub предоставит Вам Client ID и Client Secret

    УЗапишите в REDIS_HOST ваш host, а в REDIS_PORT ваш порт (по умолчанию 6379). \
    Запустить Redis можно при помощи команды:

    ```bash
    docker-compose up redis
    ```

2. Создать и активировать виртуальное окружение:

    ```bash
    python -m venv .venv
    .venv\Scripts\activate
    ```

3. Установить необходимые зависимости:

    ```bash
    pip install -r requirements.txt
    ```

4. Применить миграции

    Команда для применения всех существующих миграций: \
    ```bash
    alembic upgrade head
    ```

    Для отката последней миграции используйте команду: \
    ```bash
    alembic downgrade -1
    ```

5. Запустить приложение

    ```bash
    uvicorn app.main:app
    ```

## Описание миграций

Миграция "Initial tables" была создана при помощи команды: \
alembic revision --autogenerate -m "Initial tables" \
Она инициализирует таблицы.

Миграция "Add users, news and comments" была создана при помощи команды: \
alembic revision -m "Add users, news and comments"

Эта миграция создаёт трёх пользователей с разными ролями (admin, author, user), одну новость и два комментария, написанные разными пользователями. При откате данной миграции база данных полностью отчищается от всех данных, в том числе от тех, которые были созданы после применения этой миграции.

Пароли пользователей хранятся в базе данных в хэшированном виде. При тестировании для создания сессий моковых пользователей воспользуйтесь следующими email и password:

- для user_id = 1 (admin): email = 'polina@mail.ru', password = '12345678'
- для user_id = 2 (author): email = 'mitya@mail.ru', password = '87654321'
- для user_id = 3 (user): email = 'danya@mail.ru', password = '12348765'

Подробнее о том, как работает текущая ролевая модель можно прочесть в docs/auth.md.

## Структура взаимодействия с БД и Redis

Общая архитектура взаимодействия с БД и Redis при запросах на чтение новостей реализована по схеме:

Клиент → API → [Redis кэш] → [База данных]

Кэширование применяется для операций чтения новостей с целью повышения производительности сервиса. При большом количестве пользователей часто запрашиваемые данные возвращаются из быстрого кэша Redis, что значительно снижает нагрузку на основную базу данных и ускоряет время отклика.

Сессии не хранятся в БД, они взаимодействуют с сервисом только посредством Redis. Это необходимо, так как время жизни JWT токена довольно короткое, и из-за этого браузеру необходимо будет довольно часто получать сессии по refresh токену, чтобы обновить JWT и refresh токен и создать новую сессию.

## Мониторинг и логирование

Проект включает полную систему мониторинга, метрик и логирования:

### Метрики Prometheus и Grafana

Приложение экспортирует метрики в формате Prometheus на эндпоинте `/metrics`.

**Базовые метрики:**
- HTTP-запросы (количество, время обработки, статус-коды)
- Метрики производительности FastAPI

**Бизнес-метрики:**
- `news_created_total` - количество созданных новостей (с label `author_id`)
- `users_registered_total` - количество зарегистрированных пользователей
- `notifications_sent_total` - успешные отправки уведомлений (с label `notification_type`)
- `notifications_failed_total` - неудачные отправки уведомлений (с label `notification_type`, `error_type`)
- `notification_duration_seconds` - время отправки уведомлений

**Запуск Prometheus и Grafana:**

```bash
docker-compose up prometheus grafana
```

- Prometheus UI: http://localhost:9090
- Grafana UI: http://localhost:3000 (логин: `admin`, пароль: `admin`)

**Настройка Grafana:**
1. Войдите в Grafana
2. Перейдите в Settings → Data sources → Add data source
3. Выберите Prometheus
4. Укажите URL: `http://prometheus:9090`
5. Сохраните

**Экспорт метрик в JSON:**
Метрики автоматически сохраняются в JSON-файлы в директории `metrics/` каждые 5 минут. Файлы имеют формат `metrics_YYYYMMDD_HHMMSS.json`.

### Структурированное логирование (structlog)

Все логи приложения выводятся в JSON-формате для удобной обработки и анализа.

**Логирование запросов:**
- Каждый HTTP-запрос логируется с уникальным `request_id` для корреляции
- Логируются: метод, путь, статус-код, время обработки, IP-адрес, User-Agent

**Логирование ошибок:**
- Все исключения логируются с полным контекстом (путь, метод, request_id, стек-трейс)

**Переменные окружения:**
- `LOGSTASH_HOST` - хост Logstash (по умолчанию: `localhost`)
- `LOGSTASH_PORT` - порт Logstash (по умолчанию: `5000`)
- `LOG_FORMAT` - формат логов (`json` или `console`, по умолчанию: `json`)

### ELK-стек (Elasticsearch, Logstash, Kibana)

Логи отправляются в Logstash, который обрабатывает их и сохраняет в Elasticsearch для анализа в Kibana.

**Запуск ELK-стека:**

```bash
docker-compose up elasticsearch logstash kibana
```

- Elasticsearch: http://localhost:9200
- Kibana: http://localhost:5601

**Настройка Kibana:**
1. Войдите в Kibana
2. Перейдите в Management → Stack Management → Index Patterns
3. Создайте index pattern: `news-service-logs-*`
4. Выберите поле времени: `@timestamp`
5. Сохраните

**Фильтрация логов в Kibana:**
Логи можно фильтровать и сортировать по полям:
- `request_id` - уникальный ID запроса
- `method` - HTTP-метод
- `path` - путь запроса
- `status_code` - код ответа
- `error_type` - тип ошибки
- `level` - уровень логирования

### Трекинг ошибок (Hawk)

Hawk используется для автоматического отслеживания и мониторинга ошибок в приложении.

**Настройка Hawk:** 
1. Зарегистрируйтесь на https://hawk.so
2. Создайте workspace и проект
3. Получите DSN (Data Source Name) для вашего проекта
4. Добавьте DSN в `.env` файл: 

   ```
   HAWK_DSN=your-hawk-dsn
   ```

**Отправка ошибок:**
- Все необработанные исключения (5xx ошибки) автоматически отправляются в Hawk
- В Hawk отображается полный контекст ошибки: стек-трейс, путь, метод, request_id

**Проверка работы Hawk:**
1. Вызовите ошибку в приложении (например, неверный запрос к несуществующему endpoint)
2. Проверьте панель управления Hawk - ошибка должна появиться в списке

## Тестирование мониторинга

### Проверка метрик:
1. Выполните несколько запросов к API
2. Откройте http://localhost:8000/metrics - должны быть видны метрики
3. В Grafana создайте дашборды для визуализации метрик

### Проверка логирования:
1. Выполните запросы к API
2. Проверьте логи в консоли (должны быть в JSON-формате)
3. В Kibana проверьте, что логи появились в индексе `news-service-logs-*`

### Проверка Hawk:
1. Вызовите ошибку (например, запрос к несуществующему endpoint)
2. Проверьте панель управления Hawk - ошибка должна быть зафиксирована
